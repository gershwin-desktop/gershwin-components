# Observed behaviour of the real dbus-daemon 1.16.2

What the suite learned by running every scenario against `/usr/bin/dbus-daemon`
with `test-bus.conf` (permissive session-like policy, ANONYMOUS allowed, no
activation, generous limits). Where a test asserts it, the test is named in
brackets. "Real" means dbus-daemon, "minibus" the replacement. Items marked
(quirk) are surprising, are not covered by the specification and are asserted
only loosely or not at all.

## SASL [t_Sasl]

- Lines end with CRLF. A bare LF does not terminate a command; the daemon
  waits silently.
- Maximum line length is 16384: 16380 bytes is answered, 16400 closes the
  connection. 200000 bytes without a line end close it too. 100 bytes without
  a line end are simply waited on.
- After 6 failed attempts (`REJECTED`) the 7th command finds the connection
  closed (quirk; the suite only requires "eventually, within 60 tries").
- The first byte must be NUL, otherwise the connection is closed at once.
- `AUTH EXTERNAL` without argument answers `DATA` (just `DATA`, no payload);
  an empty `DATA` line then means "use the socket credentials" and yields `OK`.
  `AUTH EXTERNAL <hex uid>` with the right uid answers `OK <32 hex guid>`.
- Wrong uid: `REJECTED EXTERNAL ANONYMOUS`. The list holds exactly the enabled
  mechanisms (here EXTERNAL and ANONYMOUS), `DBUS_COOKIE_SHA1` is not offered.
  Non-hex argument: `ERROR "Invalid hex encoding"`; odd-length hex: `REJECTED`.
- Unknown or lower-case commands, empty lines, `OK x`, `REJECTED`: `ERROR "Unknown command"`.
  A NUL inside a line: `ERROR "Command contained non-ASCII"`.
- `CANCEL` without conversation: `ERROR "Not currently in an auth conversation"`;
  during the DATA exchange or after `OK`: `REJECTED ...`, and a new login is possible.
  `ERROR` from the client: `REJECTED ...`.
- While waiting for BEGIN: second `AUTH` -> `ERROR "Sent AUTH while expecting BEGIN"`,
  `DATA` -> `ERROR "Sent DATA while expecting BEGIN"`. During the DATA exchange
  `AUTH` -> `ERROR "Sent AUTH while another AUTH in progress"`.
- `BEGIN` without `OK`, or in the middle of the DATA exchange: connection closed.
- `NEGOTIATE_UNIX_FD` before authentication: `ERROR "Need to authenticate first"`.
  After `OK`: `AGREE_UNIX_FD`, and a second one is answered `AGREE_UNIX_FD` again.
  After `BEGIN` it is garbage in the message stream: connection closed.
- ANONYMOUS needs both `<auth>ANONYMOUS</auth>` and `<allow_anonymous/>`.
  An anonymous peer has no uid: `GetConnectionUnixUser` fails with
  `org.freedesktop.DBus.Error.Failed` ("Could not determine UID for ':1.0'") and
  `GetConnectionCredentials` holds only `ProcessID`.
- The bus id from `GetId` is NOT the GUID of the SASL `OK` line (the two differ
  although they share their last 8 hex digits, the time stamp).
- Auth, BEGIN and the first message may arrive in one write; replies come in order.

## Hello and unique names [t_Hello]

- Names are `:1.N`; the first Hello of a daemon gets `:1.0`. Only a successful
  Hello consumes a number. Names are not reused.
- Order on the wire: Hello reply (method return from `org.freedesktop.DBus`,
  `sig="s"`), then signal `NameAcquired(":1.N")` addressed to the new client.
- All messages generated by the bus carry the NO_REPLY_EXPECTED flag (flags=1).
- The bus always answers in its native byte order, not the one of the request.
- Before Hello, a method call to `org.freedesktop.DBus` other than `Hello`
  is answered with `org.freedesktop.DBus.Error.AccessDenied` ("Client tried to
  send a message other than Hello without being registered"), destination
  header `:not.active.yet`, and the connection stays open. A message to any
  other destination, or any signal, closes the connection. `Hello` with
  an argument: `InvalidArgs`. `Hello` without an interface header works.
  `Hello` on a wrong interface before registration: `AccessDenied` (quirk).
  `Hello` without destination: `UnknownMethod` (quirk: such a message is not
  treated as addressed to the bus).
- Second Hello: `org.freedesktop.DBus.Error.Failed` "Already handled an Hello message".
- `Hello` with NO_REPLY_EXPECTED registers the client and sends no reply.

## Message validation [t_Validation]

The real daemon never answers a malformed message, it just closes that one
connection. Everything below was seen to close the connection:
bad endianness byte, version 0/2/255, message type 0, serial 0, declared body
length above 128 MiB, declared fields length above 64 MiB, missing PATH or MEMBER
in a call, missing PATH/INTERFACE/MEMBER in a signal, missing REPLY_SERIAL in a
return or error, missing ERROR_NAME, an empty field array, invalid path
(`foo`, `/foo/`, `//`, `/foo//bar`, `/foo-bar`, ``), invalid interface (no dot,
leading dot, empty element, element starting with a digit, `-`, empty, 256
characters), invalid member (empty, digit first, dot, dash, 256 chars), invalid
destination (no dot, empty, `a..b`, 256 chars), invalid error name, duplicate
header fields, header field code 0, a field with the wrong type, REPLY_SERIAL 0,
non-zero padding anywhere (after the header, in structs, in array padding),
body shorter or longer than the signature says, a body without signature,
signatures: `z`, `(`, `(s`, `a`, `a{ss`, `{ss}`, `a{s}`, `a{vs}`, `()`, `)`, `a{sss}`, `r`,
33 nested arrays or structs, longer than 255 bytes; strings: not NUL terminated,
embedded NUL, length beyond the body, invalid UTF-8 (lone continuation byte,
0xff, truncated sequence, overlong `c0 af`/`c0 80`, UTF-16 surrogates, above
U+10FFFF, 5-byte sequences); invalid object paths and signatures in the body;
booleans other than 0/1; arrays whose length is not a multiple of the element
size, beyond the body, above 64 MiB; a missing padding after the length of a
8-byte-element array (also when empty); variants with empty/invalid/two-type
signatures; variants nested 65 deep.
Tolerated: unknown flag bits, unknown header field codes (e.g. 77 and 255 of
type `u`), serial 0xffffffff, member of 255 chars, 32 nested arrays, `U+FFFF`
and `U+10FFFF` in strings, PATH `/`, a `DESTINATION` of `:` (answered with an
error). A message of unknown type (6, 200) gets an error back (quirk; the suite
accepts "error" or "ignored"). A partial message is waited for indefinitely.
A valid message followed by garbage is answered and then the connection is closed.

## Names [t_Names]

- Reply codes: PRIMARY_OWNER 1, IN_QUEUE 2, EXISTS 3, ALREADY_OWNER 4;
  ReleaseName: RELEASED 1, NON_EXISTENT 2, NOT_OWNER 3.
- `NameAcquired` / `NameLost` reach the client BEFORE the reply to the
  `RequestName` / `ReleaseName` call that caused them.
- Asking again while queued keeps the place (IN_QUEUE). DO_NOT_QUEUE while
  queued: EXISTS, and the client is removed from the queue. Flags are updated
  when the owner asks again (ALREADY_OWNER, then replacement by others works).
- REPLACE_EXISTING against an owner that did not allow it: IN_QUEUE, or EXISTS
  with DO_NOT_QUEUE. A replaced owner goes to the queue unless it had asked
  with DO_NOT_QUEUE. One `NameOwnerChanged(name, old, new)` is sent, plus
  `NameLost` to the old and `NameAcquired` to the new owner.
- A queued client that calls ReleaseName gets RELEASED and leaves the queue,
  silently. ReleaseName of a name nobody owns: NON_EXISTENT.
- Unknown flag bits are ignored.
- `RequestName` of an invalid name, of a `:x.y` name, and of
  `org.freedesktop.DBus`: `InvalidArgs`. Elements may contain `-` and `_`,
  must not start with a digit; 255 characters allowed, 256 not.
  `ReleaseName` of `:1.x`, of `org.freedesktop.DBus`, of an invalid name: `InvalidArgs`.
- Disconnect: ownership passes to the head of each queue (NameOwnerChanged old->new,
  NameAcquired to the heir); names without a heir get NameOwnerChanged(name, old, "");
  the names are released in reverse order of acquisition and the unique name
  (`:1.x`, `:1.x`, "") goes last. A queued client that disconnects only produces
  the signal for its unique name.
- A new connection produces `NameOwnerChanged(":1.x", "", ":1.x")`.

## Bus methods [t_BusMethods]

- The method is `GetConnectionUnixProcessID` (there is no `GetConnectionProcessID`).
- Errors: `GetNameOwner` of an unknown or invalid name: `NameHasNoOwner`;
  wrong argument types: `InvalidArgs` with text "Call to X has wrong args (u, expected s)";
  unknown member: `UnknownMethod` ("org.freedesktop.DBus does not understand message X");
  known member on an unknown interface: `UnknownInterface`; a call without
  interface header is resolved by member name; the object path of calls to the
  bus is ignored (any path works).
- `GetAdtAuditSessionData`: `AdtAuditDataUnknown`;
  `GetConnectionSELinuxSecurityContext`: `SELinuxSecurityContextUnknown`; both
  `NameHasNoOwner` for missing names.
- `ListActivatableNames` returns `["org.freedesktop.DBus"]` (minibus: empty array).
- `StartServiceByName` always `ServiceUnknown` ("The name X was not provided by
  any .service files"), also for names that are currently owned and for the bus
  name itself.
- `UpdateActivationEnvironment` and `ReloadConfig` are accepted (empty reply).
- Properties: `Features` = `["ActivatableServicesChanged","HeaderFiltering"]`,
  `Interfaces` = `["org.freedesktop.DBus.Monitoring","org.freedesktop.DBus.Debug.Stats"]`;
  `Get` of unknown property `UnknownProperty`, of unknown interface
  `UnknownInterface` (also for ``), `Set` of a known property `PropertyReadOnly`;
  `GetAll` of the Monitoring interface is an empty `a{sv}`.
- Introspection of the bus is returned for any path, and also lists
  `org.freedesktop.DBus.Debug.Stats` (minibus need not).
- NO_REPLY_EXPECTED is honoured only for methods whose reply is empty
  (AddMatch, RemoveMatch, ReloadConfig, ...): `ListNames` or `RequestName` with
  the flag are answered anyway (quirk).
- `GetConnectionUnixProcessID(org.freedesktop.DBus)` is the daemon pid.

## Match rules [t_Match]

- The empty rule is valid and matches every broadcast. A trailing comma and a
  rule like `=x` are accepted (quirk). `argNpath='a'` and `'/a//b'` are accepted
  (not validated). `type=signal` without quotes works. `\\'` is NOT an escape inside
  quotes; the form `'it'\''s'` (close, escaped quote, reopen) is what works.
- argN matches only string arguments; object paths match only via `argNpath`.
- argNpath follows the specification examples. argNnamespace matches the
  namespace itself and `ns.` prefixed names, not `nsx`.
- A broadcast without any matching rule is delivered to nobody. Messages
  addressed to a client are delivered regardless of its rules, so `interface='other'`
  does not block a unicast signal. A sender gets its own broadcast only when its
  own rules match.
- Identical rules may be added several times; a message is delivered once;
  RemoveMatch removes one instance; the key order in RemoveMatch does not matter.
- `sender='well.known'` follows the owner of the name.
- Invalid: unknown key, `type='bogus'`, unterminated quote, empty key/value
  combinations, duplicate keys, bad path/interface/member/sender/destination,
  `path` together with `path_namespace`, `arg64`, `eavesdrop='maybe'`.

## Monitors [t_Monitor]

- The method lives on `org.freedesktop.DBus.Monitoring`
  (`BecomeMonitor(as, u)`), not on `org.freedesktop.DBus`.
- After the (empty) reply the monitor gets `NameLost(<its unique name>)`: it
  loses its unique name. It disappears from `ListNames`, and watchers see
  `NameOwnerChanged(":1.x", ":1.x", "")` at that moment (not again on close).
- Anything a monitor sends (call, signal, even a call to the bus) closes the
  connection. A second BecomeMonitor closes it too.
- It sees method calls (also those to the bus), returns, errors, signals,
  NameOwnerChanged, NameAcquired of others, unicasts to others, undeliverable
  calls and their errors, with the headers as the receiver sees them.
- Rules are OR-ed, an empty rule list or `""` means everything; flags other than 0:
  `InvalidArgs` ("BecomeMonitor does not support any flags yet"); a bad rule:
  `MatchRuleInvalid` and the connection stays a normal client.
- Monitors that never read are NOT dropped (the whole stream is queued) [t_Scale].

## Routing [t_Routing]

- Forwarded messages keep serial, path, interface, member, destination (a
  well-known destination stays as written), flags and body; SENDER is always
  replaced by the sender's unique name (a bogus SENDER from the client is
  overwritten; an invalid one is dropped silently or the sender is dropped).
- Unknown destination (well-known or unique): `ServiceUnknown` ("The name X was
  not provided by any .service files") from `org.freedesktop.DBus`, even for
  calls with NO_REPLY_EXPECTED and for unicast signals.
- Callee disconnects without replying: `NoReply` ("Message recipient
  disconnected from message bus without replying"). Not for answered calls and
  not for NO_REPLY_EXPECTED calls.
- With a permissive policy the daemon forwards replies nobody asked for, replies
  from a third party and duplicate replies. (The stock session.conf denies them;
  minibus has no policy.)
- A client sending to a unique name that does not exist: error `ServiceUnknown`.
  A reply to a vanished caller is dropped silently.
- A broadcast reaches the sender if its rule matches.
- A valid message cut into single bytes, random chunks, 1000 messages in one
  write, 300 pipelined calls: all work.

## File descriptors [t_Fds]

- Negotiated peers: fds travel in calls, returns and broadcasts, every
  receiver gets its own descriptors, up to 16 per message; 17 close the
  sender's connection.
- Receiver without negotiation: the sender gets
  `org.freedesktop.DBus.Error.NotSupported` ("Tried to send message with Unix
  file descriptorsto a client that doesn't support that."), nothing is delivered
  and both connections live on. A broadcast is skipped for such clients.
- Sender without negotiation that sends an fd: sender disconnected.
- UNIX_FDS header larger than the fds that came with the message: sender
  disconnected. Smaller: the message is delivered with the header count of
  descriptors, but the daemon keeps the surplus descriptor in a per-connection
  queue and attaches it to the next message with fds, in both directions
  (quirk; the suite uses throw-away connections for it).
- The body is not checked against the fds: `h` indexes beyond the count or no
  `h` at all are delivered unchanged.
- Descriptors may arrive with any chunk of the message bytes.

## Scale [t_Scale]

- The real daemon needs about four descriptors per connection (socket, pidfd,
  ...), so with the 4096 hard limit of the test user it serves roughly 1000
  clients; beyond that it stops answering (100 percent CPU in accept) instead of
  refusing. The suite uses 900 clients for real and 1100 for minibus
  (`MINIBUS_TEST_CLIENTS`).
- `max_outgoing_bytes` (8 MB in `test-bus.conf`): a reader that never reads
  keeps its connection, but the daemon stops queueing for it after about that
  many bytes; other clients stay responsive (round trips below 2 s during a
  96 MiB flood). Monitors have no such bound.
- A client that sends many requests without reading gets all answers later.

## Command line [t_Cli]

- `--print-address[=fd]` prints `unix:path=...,guid=<32 hex>`, `--print-pid[=fd]`
  the pid; with both (`=1`) the address comes first. A bare `--print-pid` takes
  the NEXT argument as its descriptor, so it must come last.
- There is no `--pid-file` option (config `<pidfile>` instead). `--nopidfile`
  exists.
- SIGTERM: exit status 0 and the socket file is removed. SIGINT: the process is
  killed by the signal (default action) and the socket file stays behind
  (quirk). SIGHUP reloads the configuration and keeps running. SIGUSR1 kills it.
- A stale socket file is replaced.
- A live socket IS STOLEN: a second daemon on the same path starts and unlinks the
  first one's socket, which becomes unreachable (minibus must refuse).
- An address in a missing directory and unknown options: exit status 1.
- Clients that vanish with answers pending, also with RST, do not hurt (SIGPIPE).
