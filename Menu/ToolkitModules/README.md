# ToolkitModules

Part of Menu: the protocol these modules speak is `../GNUStepMenuIPC.h`.

They show the menu bar of GTK 2/3/4 and Qt 5/6 programs in Menu.app, using the same
Distributed Objects protocol (`org.gnustep.Gershwin.MenuServer` and
`org.gnustep.Gershwin.MenuClient.<pid>`) that GNUstep applications use through the Eau
theme. No D-Bus is involved.

Nothing here is built against GTK, GLib or Qt: there are no headers, no development
packages and no link dependency. The modules are loaded into a process that already runs
the toolkit and call its functions by symbol name. One binary serves both major versions
of each toolkit. Build time needs only GNUstep base.

    make
    make install        # PREFIX defaults to /System/Library/Libraries/appmenu-do
    export GTK_PATH=/System/Library/Libraries/appmenu-do GTK_MODULES=gtk-appmenu-do
    export GIO_EXTRA_MODULES=/System/Library/Libraries/appmenu-do/gio/modules
    export QT_PLUGIN_PATH=/System/Library/Libraries/appmenu-do QT_QPA_PLATFORMTHEME=gad

`QT_QPA_PLATFORMTHEME=gad` only starts the module and then declines to be a theme; Qt goes on with the next name of the list, so put `gad` first and the real theme after it (`gad:kde`, `gad:gtk3`). A theme listed before `gad` is used and stops the search. The session scripts do this.

## Layout

- `core/`: what both modules share. `bridge.m` is the Foundation-only Distributed Objects
  side on its own thread (registers the client name, reconnects to the server, converts
  the item tree to the dictionaries Menu.app expects). `node.c` is the plain-C menu tree
  with the pure helpers (accelerators, signatures), `mainsync.c` runs a function on the
  toolkit's GLib main loop from the Distributed Objects thread.
- `gtk/module.c`: a GTK module. On the first map of a `GtkMenuBar` it walks the items,
  pushes them to Menu.app, hides the in-window menu bar while Menu.app is reachable and
  pushes again (debounced 100 ms) when items change.
- `gtk4/`: GTK 4 has no modules, but GLib loads the GIO modules of `$GIO_EXTRA_MODULES`
  in every program. `gio-stub.c` is such a module, tiny and without dependencies; only in
  a program that runs GTK 4 does it load `libgad-gtk4-core.so`, which brings Foundation.
  `gtk4.c` finds the `GtkPopoverMenuBar` of each window and reads its `GMenuModel`
  (labels, sections, submenus, `accel` attributes, application accelerators). GTK 4 keeps
  the state of a window's own actions to itself, so those items are shown enabled;
  `app.` actions are asked directly. Activation is `gtk_widget_activate_action_variant`.
- `qt/`: a Qt platform theme plugin that is no theme. Qt loads it when it creates its
  platform theme (`QT_QPA_PLATFORMTHEME=gad`), on the main thread; the plugin declines to
  provide a theme, so Qt uses its own. Qt 6 only accepts a platform plugin built for
  exactly the minor version it runs, so `qtplugin.c` is built once per minor (6.2 to 6.40,
  `libgad-qt6-N.so`, a few kilobytes each) plus one for Qt 5; each loads the single copy
  of the real code, `libgad-qt-core.so`. The plugin metadata (an ELF note for Qt 6, two
  sections for Qt 5) is generated by `qt/tools/gen-qt-metadata.py` and checked in
  (`make metadata`). `qt/qt.c` finds the menu bars (`QMainWindow::menuWidget`, else `qt_qFindChildren_helper` below the window) and reads `QAction`
  texts, state, shortcuts and submenus through the C++ symbols of the loaded Qt libraries
  and the memory layout of `QString` and `QList` (different in Qt 5 and Qt 6). Qt's native
  menu bar is switched off for the program, otherwise Qt hands its menus to a D-Bus
  registrar if one is on the bus.
- `core/poller.c`: what Qt and GTK 4 share, since neither can be watched with signals from
  plain C. It looks at the program every 500 ms on the GLib main loop, sends a change,
  hides the in-window menu bar while Menu.app is reachable, and answers activation, state
  and refresh requests of Menu.app on the main thread.

## Tests

    make test     # ObjectTesting unit tests (tests/Unit)
    make check    # unit tests plus end to end runs against a mock Menu.app on a private
                  # Xvfb display: GTK 3 (menu, key equivalents, check state, menus filled
                  # on use, GMenuModel bar), a GTK 2 program when its headers exist, and
                  # Qt 5 and Qt 6 through PyQt when installed

`GAD_MENU_SERVER_NAME` renames the server so a running Menu.app is not touched.

## Known limitations

- Menus a program fills only when they are used are filled by emitting the signal that
  announces it: GTK "show", "select" (undone at once) and "activate", Qt `aboutToShow`.
  When the user starts using the menu bar, Menu.app calls `refreshedMenuDataForWindow:`
  and the module asks again, so menus rebuilt on every use change too.
- Key equivalents are single keys with modifiers; function keys, arrows and key
  sequences are not passed on. Control is sent as Command.
- GTK 4: items of window actions are always shown enabled, and a program that does not
  use a `GtkPopoverMenuBar` (client-side header bars, popover buttons) has nothing to hand
  over.
- Qt: the menu bar of a `QMainWindow`, or the first `QMenuBar` below any other top-level
  widget, is found; only QtWidgets, not Qt Quick or QML menu bars (they would have to be read
  through the meta-object system, whose calling convention differs between Qt 5 and 6). The Qt libraries must run on a GLib main loop, which is the default on Linux.
  The `QString`, `QList` and vtable layouts are those of Qt 5.15 and Qt 6.8 and were
  checked on 6.11. The module tests them on known values (a string made with `QString::fromUtf8`, the virtual table of the first window) and switches itself off with a message instead of reading a Qt that differs; a Qt 6 older than 6.2 or newer than 6.40 has no matching plugin file.
- On NextBSD and the other BSDs Foundation is told the process arguments by the module,
  since only Linux's C runtime hands them over.
